## 製品仮説

個人開発者や小規模チームでは、フロントエンド、API、アプリ、文書が別のリポジトリに分かれます。Issueやコミットを見る前に、**何を作るプロジェクトか、どのリポジトリを開くか、今何が使えるか**を把握したいと考えています。

初期の特徴は、複数のリポジトリを**ユーザーが定義するプロジェクト**にまとめ、構成要素ごとのデプロイ根拠を並べることです。一つのリポジトリでも一つのプロジェクトになります。GitHub Projectsは業務追跡、DeepWikiは個別リポジトリの説明を担います。

## 対象ユーザーと最初の画面

- 複数のサイドプロジェクトを持つ開発者と、複数リポジトリを管理する小規模チームが対象です。
- カードにはアイコン、名前、一行の目的、短い説明、状態、代表的なリリース根拠または確認状態を表示します。
- 詳細には役割、ホスティング、言語、Star・Watch・Fork、直近一年の週間コミット、最新安定版とバージョン、出典、最終確認時刻、ユーザーまたは構成要素の流れを表示します。任意項目は確認データがある場合に表示し、開閉と週別の値はキーボードに対応します。
- 一覧では名前・説明・リポジトリ検索、状態フィルター、リポジトリ・リリース・デプロイ先への移動を提供します。

## MVPの利用手順

1. ログインせずに公開GitHub・GitLab.comのURLを貼り付け、重複を除去します。非公開、削除、一時障害は判別できる範囲で説明します。
2. 公開メタデータとREADMEからカードの下書きを作ります。READMEがなければ確認できた名前と説明を入れ、空欄は編集可能にします。
3. カードの統合・分割、Web・API・文書などの役割指定、目的・説明・アイコン・流れの編集を行います。流れの例はユーザー → Web → APIです。
4. ブラウザーに保存して再度開きます。MVPの保証範囲は同じブラウザー内です。
5. ユーザー操作で取得情報を更新し、ユーザー編集を保持します。失敗時は最後の確認値と失敗時刻を表示します。

## データと表示基準

| 情報 | 基準 |
|---|---|
| 目的・説明・流れ | ユーザー入力を優先し、次にREADMEかリポジトリ説明を使用。将来のAI要約も編集可能な下書きとして表示します。 |
| 開発状態 | 企画・開発・テスト・運用・保留をユーザーが指定します。コミット頻度から推定しません。 |
| プラットフォーム・言語 | リポジトリごとに表示。GitHub言語比率はバイト合計から計算し、主要言語のみ判明した場合は名前を表示します。 [言語API](https://docs.github.com/en/rest/repos/repos#list-repository-languages) |
| Star・Watch・Fork | `stargazers_count`・`subscribers_count`・`forks_count`を使用。0は表示し、欠落は省略します。旧`watchers_count`はStar数です。 [Watch API](https://docs.github.com/en/rest/activity/watching) |
| コミット活動 | GitHubデフォルトブランチの直近一年を週別棒グラフで表示し、マージを除外。週開始日、件数、出典リンクを示します。`202`は再取得し、`204`や未取得時は新規チャートを省略します。更新失敗時は前回値と確認時刻を保持します。 [統計API](https://docs.github.com/en/rest/metrics/statistics#get-the-last-year-of-commit-activity) |
| 最新安定版 | 公開された正式なGitHub Releasesを使用し、プレリリースは別に表示。タグ単独ではリリース根拠が不足します。 |
| デプロイ根拠 | ユーザー登録のデプロイ・ストア・ダウンロード・文書リンクを種類別に表示。URL登録だけでは稼働やデプロイを検証できません。 |
| 公開状態・現在版 | 構成要素別に表示。公開文書だけではアプリ公開を証明できません。照会成功でも根拠がなければ公開未確認、照会失敗は取得失敗と表示します。 |

最小モデルはプロジェクト、ホスティングとURLを持つリポジトリ、役割・順序を持つ関連、流れの段階、出典・確認時刻を持つ版とデプロイ根拠です。言語、指標、活動は任意のリポジトリデータとして出典とともに保存し、ユーザー編集と分離します。

## 他サービスの検討

| サービス | データと条件 |
|---|---|
| GitLab.com | プロジェクトAPIでStar・Forkと言語比率を取得。期間指定したデフォルトブランチのコミットを集計します。公開Watch数は応答にないため省略。 [プロジェクト](https://docs.gitlab.com/api/projects/) · [コミット](https://docs.gitlab.com/api/commits/) |
| Bitbucket Cloud | `language`とコミットを使用。Watch・Forkは別のページ付き一覧で取得可能な範囲を確認し、言語比率とStarの省略を検討します。 [リポジトリ](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-repositories/) · [コミット](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-commits/) |
| Codeberg | ForgejoベースでWatch・Star・Forkと活動を提供。匿名API、言語・コミット応答をインスタンス上で確認してから連携します。 [案内](https://docs.codeberg.org/getting-started/first-repository/) · [Forgejo API](https://forgejo.org/docs/latest/user/api/usage/) |

公開GitHubとGitLab.comを対象とします。GitLabはコミット時刻をUTC日曜開始の52週に集計し、今週を含めマージを除外します。期間内をすべて取得できなければチャートを省略します。

## 実装方針と安全基準

- 既存カード・検索・詳細UIを再利用し、公開照会と自動更新値を分離します。Releases、README、メタデータには[GitHub REST API](https://docs.github.com/en/rest)を使用します。
- GitHub・GitLab.com URLを解析し、定められたAPIに要求します。READMEは信頼しない入力として扱い、実行可能なHTMLを除去します。
- 外部要求はキャッシュと制限を設け、上限時に案内します。サーバートークンをブラウザーに露出させません。
- AIなしで利用できる形から始めます。将来AIを使う場合もREADME内の指示には従わず要約データとして扱い、非公開内容の外部AI送信には別途同意を求めます。
- 将来の非公開連携では[GitHub App](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party)で選択したリポジトリの必要な読み取り権限を要求します。非公開カードの公開共有は初期設定で防ぎ、解除時の同期停止と削除方針を整えます。

## 初期合格基準

- 公開URL三つを追加し、二つを一枚にまとめ、**三分以内**に目的・役割・最新リリースと根拠リンクを確認できます。
- 正式版のみ、プレリリースのみ、タグのみ、READMEなし、上限到達が混在しても誤った公開表示をしません。
- Watch 0と未提供を区別し、コミット準備中や取得失敗を0件と表示しません。まとめたリポジトリも各自の確認済み言語と指標を表示します。
- 再読み込みと情報更新後も編集内容を保持します。
- 初期ユーザー五人に作成を依頼し、三人が援助なしで最初のカードを完成、二人が七日以内に再訪または更新するかを方向判断に使います。小規模実験の結果の一般化は避けます。

## 順序と事業仮説

1. 公開取り込み、編集、グループ化、公開根拠の表示。
2. 初期ユーザーを観察し、共有需要が高ければポートフォリオ生成、再訪・更新需要が高ければ管理ツールに絞ります。
3. 継続利用を確認してから非公開連携と自動更新の有料化を検証します。価格は未定です。

初期対象外はBitbucket・Codeberg、コード全体のAI解析、チーム権限、デプロイ自動化、決済、公開ポートフォリオのホスティングです。
